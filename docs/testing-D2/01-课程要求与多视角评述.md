# 课程要求与多视角评述

## 1 结论与证据边界

老师要求的是可运行系统及可检查、可重复的工程证据。界面美化能改善使用体验，但不能替代数据贯通、异常处理、AI 评价和测试留档。

审阅材料共 169 页：`01_AI_Era_Software_Engineering(1).pdf` 59 页、`02_Requirements_and_Object_Oriented_Analysis.pdf` 66 页、`Project_Kickoff.pdf` 44 页。页码均为 PDF 自身的 1 起始页码，不是幻灯片内印刷编号。完整提取并审阅文本；另渲染核查 Kickoff 第 13 页和 Lecture01 第 15 页的校历图。

分析使用用户指定的 `E:\学习工具\.codex\skills\learning-loop\SKILL.md` 及其 `references/experts/` 下学者、实践者、怀疑者、经济学家、历史学家、证据审查员规则。学者独立完成审阅；怀疑者和经济学家子代理提供了部分发现后因额度限制中断；其余角色及综合证据审查由主助手按角色框架完成。以下是五视角分析，不声称完成五位独立专家会审；同一源码或讲义被多角色引用只算一份证据。

## 3 必须正确理解的事项

- **英文要求**：针对提案/最终汇报与最终报告，未见产品 UI 必须英文。因此本次中文化可以执行。
- **截止日期**：Kickoff p44 的 2026-09-29 23:59 是团队信息截止时间。两张校历没有提案/期末截止日期文字标注，不可凭颜色推断。团队自己的调研安排也不能说成老师截止时间。
- **提案页数歧义**：Kickoff p7 同时出现“One proposal slide per team”和“Submit the slides as a PDF”。一组一份 PDF 明确，但是否只能一页不明确，正式制作时应核对后续通知。
- **访谈与指标**：三份材料没有规定访谈人数、问卷样本、准确率、覆盖率、性能阈值、报告页数。本文后续提出的数量和门槛均是团队建议，不是教师规定。
- **真实外部动作**：Kickoff p34、p38 的真实地图/日历执行属于特定选题，不能推导 ApplyGuard 必须实际投递。按用户要求，模拟 ATS 继续不真提交。
- **课堂练习**：需求讲义 p58 的领域模型、SSD 和短契约是 15 分钟个人练习；不直接升级为最终必须独立提交的三份文件。
- **设计参考**：腾讯校招表单、awesome-design-md、中文化来自用户的产品要求，并非教师原文。

## 5 五视角评述

### 学者 机制与证据

关键判断：测试通过只能支持测试所覆盖的主张。79 项通过不能证明手动新增陈述也经过后端核验；旧基准也不能证明当前中文种子效果。证据级别分别是第一方课程要求、代码事实和本轮工程测量，均不等于真实用户研究。

反例：把全部陈述都阻断也能得到“错误陈述阻断率 100%”；本轮基准恰有 28/28 负例被阻断，但 12/12 应非阻断样例同样被阻断。因此同时报告正确接受与误阻断及分母。

最小先修：操作契约、版本、不变式、预期与实际、混淆矩阵。诊断题：上传新 PDF 失败时，旧简历、证据图、匹配结果各应变还是不变？答不清则测试规格尚未完成。

### 实践者 完整操作链

最小真实流程：可选 PDF 或空白表单 → 修正基本信息/经历/竞赛 → 保存并重启读回 → 输入中文 JD → 看要求及来源 → 增删陈述并重新核验 → 模拟填写 → 人工复制 → 留下同版本的审计摘要。

已证实卡点：编辑与后端种子脱节；保存异常仍报成功；构建产物由后端独立提供时种子和预录资源 404。第一次练习是修改一个有明显区别的项目，再验证最终稿使用新内容。迁移任务是换第二位虚构候选人、第二份 JD，确认旧证据完全退出。

失败信号不能只看红字；看请求中有无新版本、磁盘是否读回、复制稿是否同源。向学者追问：页面“99%”究竟是相关分数、证据置信度还是覆盖率？

### 怀疑者 失败链与停止线

1. 前端给手动句标待复核 → 用户确认 → 未经后端核验进入复制稿。浏览器已复现；后端单独检查该未知 claim ID 为 BLOCKED。
2. 改 JD 或经历但旧结果有效 → 新原文配旧匹配、旧源配新个人信息 → 用户误以为是当前材料结论。已复现。
3. 宽泛中文桥接词将 PyTorch/LoRA 等同多模态经验 → 98.35% 强匹配 → 产生能力覆盖错觉。离线接口已复现；不是认定种子陈述本身虚假。

最强反例：完全不存在于证据库的“独立负责千万用户推荐系统，获全国竞赛一等奖”。停止线：此类内容仍能进入复制稿时，不宣布护栏验收通过。真实模型、OCR、真实用户成功率本轮未测，不能泛化。

### 经济学家 时间与机会成本

| 选择 | 主要成本 | 收益与承担者 | 建议 |
|---|---|---|---|
| 先修版本贯通、核验、保存 | 数据契约与回归投入 | 求职者少误用，团队有可证明主流程 | 第一优先 |
| 先全面换视觉主题 | 页面迁移、截图重建、返工 | 首屏更整齐，但不能消除错误结果 | 核心护栏后进行 |
| 文本 PDF 起步，识别后可编辑 | 字段提取与错误恢复 | 可控的可选导入体验 | 先确定支持边界；扫描件明确提示或后续 OCR |
| 接真实招聘站点 | 适配、登录、外部副作用维护 | 本次范围收益不必要 | 当前保持模拟 |
| 每轮调用真实模型 | 耗时、费用、随机波动 | 补充实际模型质量证据 | 先离线阻断缺陷，再固定配置小样本实测 |

令剩余可用工时为 H（尚无团队真实预算），建议情景：保守 H 只够核心时先修 P0 和数据闭环；基准在此基础上做 PDF/竞赛；充裕再做跨浏览器、性能、可用性及视觉细修。不报虚构工期或收益率。敏感参数是 PDF 复杂度、证据版本改造范围、团队并行程度；分别用小样本解析、单版本贯通、责任表验证。

最小价值验证：在同一任务上比较“直接从经历库整理”与“可选 PDF+修正”的完成时间、修正次数、遗漏项。先验证导入是否真的节约时间，再扩展 OCR。无真实受试记录时只保留方案。

### 历史学家 版本演进与遗留约束

观察范围限本仓库，不作行业历史推断。第一方材料：`HANDOFF.md`、`B_TO_C_HANDOFF.md`、`C_TO_D_HANDOFF.md`、`docs/D-2-更新说明.md`、`git log`。

| 转折 | 可核查事实 | 留下的约束 |
|---|---|---|
| A/B 提案基础 | JSON 契约、固定种子、确定性匹配与选择 | 数据适合演示，未提供编辑持久化契约 |
| C 工作流（`c80be1e`） | 模型解析、原文核对、陈述核验、风险、离线回退 | ATS 仍用 fixture，审计非后端持久化 |
| D 前端（`015384e`） | 中文表单、审查、模拟与本地历史 | 前端编辑和本地确认未自动成为后端事实 |
| D-2（`816a246`） | 模型回退标签和中文 JD 解析修复 | 未承诺 PDF/后端草稿；种子中文化要求同步迁移测试数据 |

这解释了缺口的来源，不构成验收豁免。提案允许脚手架与最终要求连通数据的适用阶段不同。重写 UI 无法自动消除固定种子架构；保留契约边界、逐段替换数据来源更便于复测。

## 7 设计参考如何落地

已核查 [VoltAgent/awesome-design-md](https://github.com/VoltAgent/awesome-design-md)。其自述是从公开网站分析提取的设计文档，不应称为各家公司官方、完整且永远精确的设计系统；历史 star 数不作为技术验收依据。

D-2 已有 `frontend/design/DESIGN.md`，顶部为 Mintlify 分析；`frontend/src/index.css:1` 明确引用该项目。后续宜保留既有中性色、绿色强调、12px 卡片和清晰表单密度，增加中文字体回退、保存/未保存状态、输入错误、键盘焦点和弹层规范。腾讯风格在这里指分组、编辑、下拉和保存反馈；不声称本轮已核查当前腾讯招聘网站的全部页面。

视觉验收用固定视口截图和操作任务，不能只用“像腾讯”“像大厂”判通过。来源、采用范围、改动与第三方声明应同步记录；当前第三方说明尚未列出该设计参考，建议补充来源记录。
